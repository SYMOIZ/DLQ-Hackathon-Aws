The problem

DLQs fill up silently. Clearing them is manual, repetitive and risky: redriving a bad message fails again, and deleting a good one loses data.

Backend / platform engineer
Pain today
Reads messages one by one to decide redrive or delete.
What DLQ Judge does
Sorts the whole DLQ and acts on the safe cases.
On-call engineer
Pain today
Bulk redrive replays poison messages and re-floods the DLQ.
What DLQ Judge does
Holds back poison messages and redrives only transient failures.
Team lead
Pain today
No record of why messages were dropped.
What DLQ Judge does
Gives an audit log of every action with its confidence.

One decision per message, three confidence bands

Run one command and get every message sorted, safe actions applied, and a report in under a minute for a few hundred messages.

Five actions

The question for every message: "What is the safest next action for this failed message?"

Redrive nowredrive_nowTransient failure that is already overSend back to the source queue
Redrive laterredrive_laterThrottling or downstream outageSend back with a delay
Quarantinequarantine_poisonBad payload or schema; will always failMove to S3 quarantine
Discard duplicatediscard_duplicateAlready processedDelete from the DLQ
Escalate to humanescalate_humanUnclear or high-riskLeave in the DLQ and flag in the report

Safety rules, always on

✓
Dry run by default
Actions need an explicit apply step or the --apply flag.
✓
Discard needs ≥ 0.90 confidence and an idempotency key
Any discard below 0.90 is flagged and held in the DLQ.
✓
Every decision is logged
Each action is stored with its option probabilities for audit.
✓
No secrets sent to the model
Message bodies are truncated and PII-masked before scoring.
✓
Bedrock calls are capped per run
Every call is logged; Bedrock can confirm or block, never act alone.

Where Bedrock is used

Second opinion
For messages at 0.60–0.85, Bedrock picks one of the same five options with a one-line reason.
Cluster diagnosis
Quarantined messages are grouped by error type; Bedrock returns a likely root cause and a suggested fix.
Run report
A short team summary of what was redriven, quarantined, discarded and escalated, and why.
Every explanation cites message IDs and error fields. Claims without evidence are labelled unverified. Bedrock never triggers an action alone.
